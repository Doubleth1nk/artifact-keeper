- **A pending password change on any admin other than the built-in `admin` no longer arms the first-run setup gate or gets `admin`'s password overwritten on restart** (#4634). At boot, `provision_admin_user` looked at the first row of `SELECT ... FROM users WHERE is_admin AND external_id IS NULL LIMIT 1` (no `ORDER BY`), so once other admins existed that had been created with a temporary password and not yet logged in, one of them could be the row returned. The gate armed on its flag, `/api/v1/setup/status` reported `setup_required: true` and every route except `/api/v1/auth/*` and the password-change endpoint returned 403 `SETUP_REQUIRED`, which looks like the login page failing for everyone. When `<STORAGE_PATH>/admin.password` was missing (any ephemeral volume, for example Kubernetes with `persistence.enabled: false`) the boot then generated a random password and wrote it to the `admin` account, replacing an operator-supplied `ADMIN_PASSWORD` that had nothing pending. Every further restart repeated it while any admin was still pending.

  The gate, the password regeneration and the runtime re-check (`setup_still_required`) now concern only the account named `admin`; if it has been renamed or removed and another local admin exists, boot creates and arms nothing. The runtime unlock and re-arm paths use the same definition: another admin rotating its temporary password no longer clears the gate on that replica while `admin` is still pending, other replicas no longer stay locked after `admin` rotated because some other admin is still pending, and reactivating another pending admin no longer re-arms it. Other admins with a pending change are still forced to rotate at their own login (the per-user 428 in the auth middleware is unchanged).
